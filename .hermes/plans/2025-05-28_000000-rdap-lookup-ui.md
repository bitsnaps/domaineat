# Plan: Expose RDAP/WHOIS Domain Lookup in UI

## Goal
Surface live domain lookup (RDAP + DNS) data to users in two places.
1. **Domain Search page** (`DomainSearchView.vue`) — standalone lookup page for arbitrary domains with flexible TLD exploration.
2. **Domain Detail page** (`DomainDetailView.vue`) — integrated tab/card showing live RDAP data for already-tracked domains.

## Context & Assumptions
- Backend RDAP endpoints already exist:
  - `GET /api/validate?domain=example.com` — returns `{ available, whois, dns }`
  - `GET /api/search?domain=example.com&tlds=com,net,org` — returns `{ results: ExtCheckResult[] }`
  - `GET /api/bulk` — returns `{ results: BulkResult[] }`
  - `GET /api/domains/:id/analyze` — returns `{ parsed, extensions, rdap }`
- Tier limits for RDAP are defined in `auth.ts` but not enforced anywhere in the API currently.
- The frontend uses Vue 3 + Pinia + Bootstrap 5, `<script setup lang="ts">` syntax.
- `DomainStatus` enum and types exist in `src/types/index.ts`.
- No new third-party packages are needed (uses `fetch`/`axios` already present).

## Proposed Approach
Keep the UI thin. Reuse the existing domain-analysis backend and compose two views.

### 1. Domain Search Page (new view)
A dedicated `/search` route with two interaction modes:
- **Single domain deep-dive**: Enter `example.com` → call `/api/validate` → show WHOIS card + DNS card + availability badge.
- **Multi-TLD explorer**: Enter keyword (e.g. `mybrand`) → select/view multiple TLDs → call `/api/search?domain=mybrand` → show a table of results (available vs taken + expiry for taken).

UI components to create:
- `DomainSearchView.vue` (page)
- `DomainLookupCard.vue` — displays a single domain's RDAP+DNS result in a card format (reused in Detail page too)
- `TldSelector.vue` — small component for picking / toggling TLDs

### 2. Domain Detail Page (extend existing)
Add a new "Live Data" tab/section on `DomainDetailView.vue` that calls `GET /api/domains/:id/analyze` on demand (lazy load on tab open / button click) and displays:
- RDAP data card (registrar, creation date, expiry, nameservers, status)
- DNS check summary (resolved? IP? SSL expiry?)
- A "Refresh" button to re-trigger the fetch (respects rate limits, shows toast on limit hit)

Tier gating:
- Free users get a lightweight experience:
  - Single domain lookup: 5/day total
  - Multi-TLD explorer: first 3 TLDs only (or 5 lookups/day total)
- Premium: 100/day
- Enterprise: unlimited

Enforcement strategy:
- Backend: add an in-memory or DB-backed counter per user for `/api/validate`, `/api/search`, `/api/analyze-domain`, and `/api/domains/:id/analyze`.
- Frontend: show remaining call count, disable / show upgrade CTA when limit reached.

## Step-by-Step Plan

### Phase 1: Backend rate-limit & refactor (1–2 dev hours)
1. Add `rdapDaily` consumption enforcement to relevant API routes.
   - `/api/validate`
   - `/api/search`
   - `/api/domains/:id/analyze`
   - `/api/analyze-domain`
2. Refactor common RDAP response shape from `app.ts` into a helper so `/api/validate` and `/api/search` return consistent, typed data.
3. Add `daily_rdap_calls` column to `User` model or use in-memory per-day counter (decide based on existing infra — DB has `daily_ai_calls`, follow same pattern).

### Phase 2: Shared components & state (1 dev hour)
4. Define shared types in `src/types/index.ts` matching backend response shapes (ValidateResult, SearchResult).
5. Create `DomainLookupCard.vue` component.
6. Create `TldSelector.vue` component with preset TLD list.
7. Add `useLookupStore` Pinia store for:
   - Search results cache (per session)
   - Daily call counter reflector (fetched from backend)
   - Loading/error states

### Phase 3: Domain Search page (2–3 dev hours)
8. Add `/search` route in `src/router/index.ts`.
9. Create `DomainSearchView.vue` with:
   - Text input for domain/keyword
   - Toggle: "Single Domain" vs "Multi-TLD"
   - TldSelector when in Multi-TLD mode
   - DomainLookupCard(s) for results
   - Inline upgrade CTA when rate limit hit
10. Wire store actions to `/api/validate` and `/api/search`.
11. Add responsive layout (Bootstrap grid, reuses existing card styles).

### Phase 4: Domain Detail integration (1 dev hour)
12. In `DomainDetailView.vue`, add a new "Live Data" tab or an expandable section.
13. On open/click, call `/api/domains/:id/analyze` via the store.
14. Display `DomainLookupCard` with the fetched data + "Refresh" button.
15. Show rate-limit remaining in the header of this section.

### Phase 5: Navigation & polish (30 min)
16. Add "Domain Search" to sidebar navigation.
17. Ensure mobile responsiveness.
18. Add basic unit tests for the new store and components (Vitest).

## Risks, Tradeoffs, and Open Questions
- **Rate-limit storage**: in-memory is fine for single-instance v0 but will not work in a multi-process deployment. Decide whether to store in DB (metadata column) or accept in-memory for now. Given `daily_ai_calls` likely exists in DB already, we should follow the same pattern.
- **Public vs. gated search**: Should `/search` be accessible without login so free-tier visitors can try it? PRD implies tiered limits, so authenticated.
- **RDAP vs raw WHOIS**: We are committed to RDAP; the API already returns structured data. Do not add new packages.
- **Performance**: RDAP queries to IANA can be slow (~1–2s). Add client-side loading states and consider 8s timeout (already in backend).
- **Error handling**: Some TLDs have no RDAP server. Ensure the UI shows "unknown" gracefully, not a fatal error.
